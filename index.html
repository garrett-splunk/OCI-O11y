OCI Monitoring → Splunk O11y

Learn how OCI Connector Hub forwards Monitoring metrics to Splunk O11y via an OCI Function and /v2/datapoint ingest. A local Python simulator sends the same payload shape — no Docker or OCI tenancy required for the core lab.

Metrics-first lab

This workshop focuses on metrics and dashboards in Splunk O11y (our internal shorthand for Splunk Observability Cloud). Log ingest to Log Observer typically requires a linked Splunk Cloud or Enterprise instance; the optional logs appendix is kept for orgs that have that integration.

OCI Connector Hub vs Oracle DB direct receiver

Both paths land in Splunk O11y, but they answer different questions. This lab covers OCI platform metrics (compute, networking, etc.) pushed from OCI Monitoring. The Oracle DB Mon workshop covers database metrics by having the OTel Collector scrape the database directly with the oracledb receiver.

When to use which

  • OCI path — You want unified cloud infrastructure metrics from Oracle Cloud (CPU on VMs, network bytes, LB requests) without installing agents on each host beyond OCI’s compute agent.
  • DB receiver path — You need deep database telemetry (locks, waits, PGA, tablespace) and can place a collector where it can authenticate to the database.
  • Both together — Common in production: OCI dashboards for the VM/autonomous service layer, DB Monitoring for query and session health. They are complementary, not interchangeable.

1 — Prerequisites

Before you start, read OCI vs DB receiver if you are unsure whether this lab or the Oracle DB Mon workshop fits your use case. This lab does not use the oracledb receiver — it simulates OCI Monitoring → Splunk O11y ingest.

  • Python 3.9+ (metrics path — no Docker required)
  • Splunk O11y ingest token with metrics ingest scope (Settings → Access Tokens)
  • Realm URLs matching your org (e.g. us1 → ingest.us1.signalfx.com)
  • Optional: Docker — only if you run the logs appendix

3 — Send OCI Monitoring metrics

Production path: Connector Hub (Monitoring → Function) transforms OCI metric payloads and POSTs Splunk O11y gauge datapoints. Locally, the same transform runs in scripts/send-oci-metrics.py (mirrors lab/functions/oci-metrics-forwarder/).

Send sample OCI metrics 
./scripts/produce-oci-metrics.sh 5

What produce-oci-metrics.sh 5 runs

  1. Shell wrapper calls python3 scripts/send-oci-metrics.py --count 5 --interval 0.5.
  2. Python loads lab/.env.splunk for token and ingest URL.
  3. Reads fixtures/oci-metric-samples.jsonl — mixed OCI namespaces (VCN, compute, LB, DB).
  4. For each line: oci_metrics_transform.py maps OCI JSON → Splunk O11y gauge body (metric, value, oci_namespace, oci_dim_*, deployment.environment.name).
  5. Stamps current timestamps, then POSTs JSON to {SPLUNK_INGEST_URL}/v2/datapoint with header X-SF-Token.
  6. Sends 5 metric events, 0.5s apart. Success: HTTP 200 in terminal output.

Fill dashboard charts

20 iterations × 30s (~10 min of counter deltas) 
./scripts/fill-occ-dashboard.sh 20 30

What fill-occ-dashboard.sh 20 30 runs

  1. Calls send-oci-metrics.py with OCC-specific options:
  2. --fixtures fixtures/oci-occ-dashboard-metrics.jsonl — oci_computeagent metrics with dashboard dimensions (resourceDisplayName, shape, etc.).
  3. --batch-all — sends every fixture line in one POST per iteration (~24 gauge points).
  4. --increment-counters — multiplies disk/network byte counters each loop so Signalflow .delta() charts show non-zero rates.
  5. --loop 20 --interval 30 — repeats every 30 seconds for ~10 minutes of time-series data.
  6. CPU/memory gauges get small variations; counters grow monotonically.

Disk and network charts use Signalflow .delta(), so the script sends increasing counter values on each iteration. CPU and memory gauges vary slightly so percentile charts move.

Script breakdown (reference)

Every command in this lab is a thin wrapper. The core work happens in send-oci-metrics.py (metrics) or Docker/collector (optional logs).

send-oci-metrics.py (shared by all metric scripts)

  1. Load SPLUNK_ACCESS_TOKEN and SPLUNK_INGEST_URL from .env.splunk.
  2. Read JSON lines from the fixtures file (default or --fixtures).
  3. oci_metrics_transform.py — same logic as the deployable OCI Function — builds Splunk O11y {"gauge": [...]} payloads.
  4. Optional: --increment-counters bumps disk/network values; --batch-all combines all fixtures per POST.
  5. HTTP POST to /v2/datapoint with X-SF-Token. Reports HTTP 200 and gauge point count.

Optional appendix — OCI logs via Streaming

Requires Splunk Cloud or Enterprise for Log Observer

Many O11y-only orgs cannot view ingested logs in Log Observer without a linked Splunk Cloud or Enterprise instance. Skip this section if you only have Splunk O11y metrics. The logs path is kept for reference and for orgs with full log integration.

Production path: OCI Logging → Connector Hub → OCI Streaming → OTel Collector (kafka receiver) → otlphttp → /v3/event.

Requires Docker

./scripts/verify-stack.sh

  3. docker compose restart otel-collector — picks up .env.splunk after you add your token.

Troubleshooting

HTTP 401 on metric export

Fix SPLUNK_ACCESS_TOKEN in .env.splunk. Ensure realm matches (US1 token → ingest.us1.signalfx.com, not us0).

Metrics in Finder but OCC dashboards empty

Run ./scripts/fill-occ-dashboard.sh 20 30 (needs oci_computeagent fixtures). Import dashboards/dashboard_group_OCC.json. Set time range to Last 15 minutes.

No logs in Log Observer

Expected if your org has Splunk O11y metrics only. Log Observer requires Splunk Cloud or Enterprise integration. Skip the logs appendix.

Collector fails to start (logs appendix only)

Use collector v0.155.0+ for kafka logs receiver. Exporter type is otlphttp (not otlp_http).
